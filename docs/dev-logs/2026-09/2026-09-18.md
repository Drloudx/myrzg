# 2026-09-18 开发汇总

## 性能（页面切换）

### 路由分包预取：消除手机端「先卡一下再切过去」

- 现象与根因（实测）：`router-view` 对懒加载路由会**等异步组件 chunk 下载完才挂载新页**，这段等待里旧页面一直挂在屏幕上不动。本机 localhost 实测切换 25~120ms（无感：`/recipes→/items` 新页 DOM 22ms / 内容就绪 97ms，最大帧停顿 70ms、零长任务），但 chunk 走网络后该延迟被放大，真机即用户感知的「卡一下」。
- 改动：`src/router/index.js` 新增两级预取（纯 `import()`，命中模块缓存，不执行页面组件）：
  1. `prefetchRouteChunks()` —— 首屏就绪后在 `requestIdleCallback` 中预取 17 个视图 chunk（约 282 KB 未压缩）；
  2. `prefetchDeferredRouteChunks()` —— 打开导航面板时补最重的 `/gacha`（单个 244 KB，占视图 chunk 近一半）。
- 触发点：`App.vue` 桌面骨架期结束处 / 移动端首屏就绪处各调一次 `prefetchRouteChunks()`；`NavigationMenu` 监听 `isOpen` 调 `prefetchDeferredRouteChunks()`。
- **并发下发会与首屏资源抢带宽**：一次并发 import 时，`卡池页资源全部可加载`（检查全部图片已解码）与 `魔物蛋卡池…`（蛋池封面解码）在并发测试下稳定失败。改为**串行 + 220ms 间隔**后 5 个套件 118 passed / 0 failed。
- 实测效果（生产产物 + CDP 网络节流，切换 `/recipes→/items|heroes|monsters|tasks`）：

| 网络 | 改动前 新页 DOM | 改动后 新页 DOM |
| --- | --- | --- |
| 本机 | 10~26ms | 11~24ms |
| 4G（RTT200/1.6Mbps） | **最高 9290ms** | **21~32ms** |
| 3G（RTT400/750kbps） | （超时） | 11~13ms |

- 首屏后已预取 17/18，`GachaView` 按设计延迟到导航意图，验证打开导航后其 chunk 才请求、随后切 `/gacha` 仅 34ms。
- 说明：预取解决的是「切换本身」的等待；页面**数据**仍按原逻辑在挂载后加载（4G 节流下约 3~6s），此时新页骨架已先显示，不再是旧页面僵住不动。

### 顺带修正的测试竞态

- `tests/ui/gacha.spec.js` 蛋池用例：切换卡池后封面是**新图**，原断言直接读 `naturalWidth` 而不等待，与图片加载赛跑（`openGacha` 的等图发生在点击切换之前，覆盖不到）。改为 `expect.poll` 等待解码完成——属测试竞态，不是页面缺陷。

## 性能（浏览器与 CDN 缓存）

### 新增 `public/_headers`（随构建产出到 `dist/_headers`）

- 背景（实测线上 `myrzg.yxzmy.top`，Cloudflare）：源站对**所有**路径都返回
  `Cache-Control: public, must-revalidate, max-age=0`，且 `must-revalidate` 下返回 **200 而非 304**（连测 3 次确认），浏览器无法复用、必须整份重传。图片另有 `max-age=3600`。
- 后果：每次重开 App / 刷新要**重下并重新 `JSON.parse`** 约 7 MB 数据
  （`items.json` 2.36MB + `heroes.json` 1.88MB + `tasks.json` 1.52MB + `monsters.json` 0.41MB + 其余），外加约 16 MB 字体。未走缓存的 `transferSize` 在刷新后逐项实测确认。
- 本项目其实**本来就具备可长缓存的条件**：`/assets/**` 文件名自带内容 hash；`/data/**` 的 JSON 按目录生成 manifest、URL 带 `?v=<该文件内容 SHA-256>`，且 `resourceClient.js` 会再校验 manifest 里的 sha256，不匹配即拒绝。缺的只是一个允许缓存的响应头。
- 新增 15 条规则（`_headers` 由 CF Pages 消费，`public/` 下随构建复制到 `dist/` 根）：

| 路径 | Cache-Control | 依据 |
| --- | --- | --- |
| `/index.html`、`/` | `no-cache`（+ `nosniff`） | 应用壳必须每次校验，否则拿不到新版本 |
| `/assets/*` | `public, max-age=31536000, immutable` | 文件名内容 hash |
| `/data/parsed/*`、`/data/dialogs/*`、`/data/taskDialogs/*` | 同上 | 各自有 `data-parsed-*` / `data-dialogs-*` / `data-taskDialogs-*` 清单校验，URL 带 `?v=` |
| `/data/notice.json` | `no-store` | 实时公告，不参与版本锁 |
| `/update/hotupdate.json` | `no-store` | **运行时热更清单**（`hotupdate.js` 的 `HOTUPDATE_MANIFEST_URL`），必须实时 |
| `/update/*.zip` | `public, max-age=31536000, immutable` | 热更包按版本号命名 |
| `/images/*`、`/ui/*`、`/fonts/*`、`/test2/*` | `public, max-age=604800` | 文件名**不带**内容 hash，资源维护会覆盖同名文件，故不给 `immutable` |
| `/_redirects`、`/_headers` | `no-cache` | 部署元文件 |

- 覆盖率核查（按 CF Pages 匹配语义模拟）：dist 内 **4803 个文件全部命中规则，0 个遗漏**（immutable 1640 / 7 天 3158 / no-cache 3 / no-store 2）。
- 格式核查：无 BOM、纯 LF、以换行结尾、15 条路径规则 + 17 条头行、仅用 `Cache-Control` 与 `X-Content-Type-Options`、无重复路径。

### ⚠️ 必须由你在控制台处理的点

**腾讯云 CDN 会覆盖本文件的策略。** 本文件只在 Cloudflare Pages 直接处理请求时生效。既然前面还有腾讯云 CDN，边缘缓存优先级更高——需在腾讯云 CDN 侧：

- 确认**「忽略查询字符串」为关闭**。否则 `?v=<hash>` 不参与缓存键，长缓存会读到旧数据（这是本方案唯一的正确性前提）；
- 配置对应的缓存过期规则，或对 `/data/`、`/assets/` 设置「遵循源站」。

### 缓存复用与传输量的权威实测（CDP）

用 CDP `Network.responseReceived.fromDiskCache` 判定（浏览器内部结论，不依赖跨域可见性），同一 URL 连测 3 次：

| 资源 | Cache-Control | 第 2/3 次请求 |
| --- | --- | --- |
| `/data/**` JSON | `public, must-revalidate, max-age=0` | ❌ 每次走网络 |
| `/fonts/*.ttf` | `public, must-revalidate, max-age=0` | ❌ 每次走网络 |
| `/images/**` | `max-age=3600` | ✅ disk cache |

用 CDP `Network.loadingFinished.encodedDataLength` 测**真实网络传输量**（手机视口，线上旧版站点，单次冷加载 `/recipes`）：

- 合计 **9608 KB / 43 个请求，0 个复用缓存**；
- 最大项：`/fonts/MYR2SansRegular.ttf` **6534 KB**、`/ui/map_w1_bg.png` 2423 KB、`/ui/logo.png` 121 KB；
- 旧版 `/recipes` 冷加载只需 ~20 KB 数据 JSON（`recipes.json` + `item-sources.json`），并非一次性拉全量数据表——**数据体积问题集中在物品/角色/任务等页**，不在首页。

据此两点确认：① `_headers` 要解决的正是「数据与字体零复用」；② 线上仍加载已废弃的 `MYR2SansRegular.ttf`（6.5 MB）与旧字体名，新版本已删除，**下次发布即省下这部分**。

### 测量方法教训（避免误判）

- **不要用 `Invoke-WebRequest` 判编码**：本次线上 `update/hotupdate.json` 被它报成「中文乱码」，实际原始字节是正确的 UTF-8（`E7 83 AD E6 9B B4 E6 B5 8B E8 AF 95` = 热更测试）。原因是响应头为 `Content-Type: application/json`（不带 `charset`），该工具按 Latin-1 解码。**结论：它显示的 `body` 串会失真，但 `Headers` 是可靠的。**
- **判 HTTP 缓存必须用 CDP 的 `fromDiskCache`**：`transferSize`/`decodedBodySize` 在跨域且无 `Timing-Allow-Origin` 时会把 `transferSize` 记成 0，容易误判为「已缓存」。
- 本次还出现过两次**无效路径取样**（用本地构建名 `/assets/index-*.js`、以及线上尚未部署的 `/images/gacha/shop.png` 去探测），返回的 507 字节其实是 SPA fallback 的 index.html。**探测线上资源前要先确认该文件确实存在。**
